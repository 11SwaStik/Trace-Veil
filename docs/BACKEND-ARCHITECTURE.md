# Traceveil — Complete Backend Architecture

> Planning reference. No implementation code — just the full system explained.

---

## 1. High-Level Backend Overview

The Traceveil backend is a multi-service Python system. Its job is to:

- Run attack simulations against virtual infrastructure
- Generate events in real time and stream them to connected browsers
- Persist every event to PostgreSQL for replay later
- Manage infrastructure node health state throughout a simulation
- Fire alerts when detection rules match events
- Serve a REST API for managing simulations, replays, scenarios, and users

The backend is **not** a monolith. It is split into discrete services that communicate primarily through Redis Pub/Sub. Each service owns exactly one concern and does not reach into another service's internals.

---

## 2. Backend Responsibilities

| Service | Responsibility |
|---|---|
| **API Service** | Public HTTP interface — auth, REST endpoints, input validation, DB writes, dispatches Celery tasks |
| **Simulation Engine** | Celery worker — runs the attack state machine, generates events, publishes to Redis |
| **WebSocket Gateway** | Holds browser WS connections open, subscribes to Redis, forwards events to clients |
| **Alert Service** | Consumes events from Redis, evaluates detection rules, writes Alert records, fires ALERT_FIRED |
| **Replay Engine** | Reads persisted events from PostgreSQL, re-publishes them to Redis at controlled speed |

---

## 3. Backend Philosophy

The backend is designed around one core idea: **events are the single source of truth**.

Everything that happens during a simulation — an attacker moving laterally, a node becoming compromised, an alert firing — is expressed as an event. Events are:

- Generated by the Simulation Engine
- Published to Redis immediately (real-time delivery)
- Written to PostgreSQL immediately (replay and audit)
- Consumed by the Alert Service (detection)
- Consumed by the WebSocket Gateway (streaming)

This means the replay system is not special. It just re-sends the same events the live simulation produced. The browser does not know whether it is watching a live simulation or a replay — it receives the same event shapes through the same WebSocket protocol.

---

## 4. Event-Driven Architecture Explanation

### What "event-driven" means here

Instead of services calling each other directly, services communicate by publishing messages to a shared bus (Redis Pub/Sub). Any service that cares about a type of event subscribes to the relevant channel.

### Why this matters

The Simulation Engine and Alert Service never talk directly. The engine publishes `LATERAL_MOVEMENT` events; the Alert Service subscribes and evaluates them independently. The simulation engine doesn't wait for alert processing — it stays fast and focused.

### Redis Pub/Sub as the event bus

Redis Pub/Sub is fire-and-forget. When the Simulation Engine publishes an event to `simulation:{sim_id}:events`, every subscriber (WebSocket Gateway, Alert Service) receives it simultaneously. Redis does not persist these messages — they are transient. Durability comes from writing to PostgreSQL separately.

### Channel naming convention

```
simulation:{sim_id}:events     # All attack/state events for a simulation
simulation:{sim_id}:commands   # Control signals (pause, resume, stop)
alerts:{sim_id}                # Alert events from Alert Service → WS Gateway
replay:{replay_id}:events      # Re-broadcast during replay playback
```

## 5. Attack Simulation Architecture

### Scenario definition

Scenarios are defined in YAML files. Each specifies:

- Name, description, MITRE ATT&CK kill chain phase sequence
- An ordered list of **steps**, each with:
  - `event_type` — RECON, LATERAL_MOVEMENT, EXFILTRATION, etc.
  - `source_node_type` — ATTACKER, WORKSTATION, SERVER, etc.
  - `target_node_type` — DATABASE, IAM, etc.
  - `ttp_id` — MITRE ATT&CK technique ID (e.g. T1078)
  - `severity` — LOW, MEDIUM, HIGH, CRITICAL
  - `delay_ms` — time before this step fires
  - `probability` — 0.0–1.0, chance this step executes (allows randomness)

### Simulation state machine

```
INITIALIZING → RUNNING → PAUSED ↔ RUNNING → COMPLETED
                                ↘ STOPPED
```

- **INITIALIZING** — topology built, node list created, Simulation record updated
- **RUNNING** — steps execute sequentially, events generated and published
- **PAUSED** — engine suspends, state preserved in Redis
- **COMPLETED** — final state written to DB, Replay record created
- **STOPPED** — terminated before completion

### Topology generation

At simulation start, the engine generates a virtual topology: a set of nodes (servers, databases, routers, IAM systems, workstations, one attacker) with network edges between them. The topology is stored as JSON in the Simulation record and broadcast as `STATE_SYNC` so the browser can render it immediately.

### Event generation loop

For each scenario step:
1. Wait `delay_ms` (adjusted by speed multiplier)
2. Pick source and target nodes from the topology
3. Build an Event object
4. Write the Event to PostgreSQL
5. Publish the Event to Redis
6. Update affected node's health state
7. Publish `NODE_STATE_CHANGE` event

## 6. Replay Engine Architecture

### Core idea

The Replay Engine is not a second simulation. It is controlled playback of events already stored in PostgreSQL. It reads the ordered event log for a completed simulation and re-publishes those events through the same Redis channels the WebSocket Gateway subscribes to.

### Replay controller state machine

```
IDLE → PLAYING → PAUSED ↔ PLAYING → COMPLETED
```

### Seek / scrub

When a user drags the timeline scrubber:
1. Replay Engine stops current playback
2. Queries PostgreSQL for all `NODE_STATE_CHANGE` events up to the target timestamp
3. Reconstructs the node state map at that point
4. Publishes a `STATE_SYNC` event with full node state
5. Resumes event playback from that sequence position

### Speed control

All inter-event delays are divided by the speed multiplier. At 4x speed, all delays are divided by 4. The multiplier is updated in real time without restarting playback.

### Replay record

When a simulation completes, the Simulation Engine creates a Replay record in PostgreSQL:

| Field | Description |
|---|---|
| `id` | UUID |
| `simulation_id` | Source simulation |
| `title` | Auto-generated from scenario name + timestamp |
| `event_count` | Total events in log |
| `duration_ms` | Wall time of the simulation |
| `created_at` | When the replay was saved |

The Replay Library UI reads from this table.

## 7. Event Generation Flow

```
Simulation Engine
    │
    ├── write Event to PostgreSQL (durable record)
    │
    └── publish Event to Redis channel: simulation:{sim_id}:events
              │
              ├── WebSocket Gateway receives → pushes ATTACK_EVENT to browser
              │
              └── Alert Service receives → evaluates detection rules
                        │
                        ├── no match → discard (contributes to detection gap)
                        │
                        └── rule matches → write Alert to PostgreSQL
                                         → publish ALERT_FIRED to Redis
                                                   │
                                                   └── WS Gateway → browser
```

---

## 8. Event Lifecycle

1. **Born** — Simulation Engine builds an Event object in memory
2. **Persisted** — Written to `events` table in PostgreSQL with UUID and sequence number
3. **Broadcast** — Serialized to JSON, published to Redis Pub/Sub
4. **Streamed** — WebSocket Gateway receives it and forwards to all browser clients in the simulation room
5. **Evaluated** — Alert Service receives it and checks detection rules
6. **Stored forever** — Remains in PostgreSQL as the basis for replay and history
7. **Replayed** — During replay, read from PostgreSQL and re-broadcast through the same pipeline

## 9. Infrastructure State Management

### Node health states

| State | Meaning |
|---|---|
| `HEALTHY` | No attack activity on this node |
| `SUSPICIOUS` | Low-severity event has targeted this node |
| `COMPROMISED` | High-severity event has successfully targeted this node |
| `ISOLATED` | Quarantined (future feature) |

### Where state lives

- **Source of truth during simulation**: in-memory dictionary in the Simulation Engine worker (`{node_id: NodeState}`)
- **Persisted**: encoded in `NODE_STATE_CHANGE` events stored in PostgreSQL
- **Reconstructed for replay/seek**: by replaying all `NODE_STATE_CHANGE` events up to the target timestamp

### State transition rules

```
HEALTHY → SUSPICIOUS    (any RECON or LOW/MEDIUM severity event targeting this node)
HEALTHY → COMPROMISED   (HIGH or CRITICAL event — skips SUSPICIOUS)
SUSPICIOUS → COMPROMISED (subsequent HIGH/CRITICAL event on same node)
```

Transitions are deterministic based on event severity and type, defined in a config table.

### State sync on connect

When a browser client connects (or reconnects) to a live simulation, the Gateway sends a `STATE_SYNC` message with the full current node state map. This ensures the topology renders correctly even if the client missed earlier events.

## 10. Alert & Detection Architecture

### Detection rules

Simple pattern-matching rules stored in the database:

```
IF event.type == LATERAL_MOVEMENT AND event.severity >= HIGH
THEN alert: title="Lateral Movement Detected", severity=HIGH
```

Rules are evaluated in the Alert Service, not the Simulation Engine.

### Alert lifecycle

1. Alert Service receives an event from Redis
2. Evaluates each active detection rule
3. Matching rule → creates Alert record in PostgreSQL
4. Publishes `ALERT_FIRED` to Redis (`alerts:{sim_id}` channel)
5. WebSocket Gateway receives it → sends `ALERT_FIRED` message to browser

### Detection gap

Some attack events intentionally match no detection rule. This is the "detection gap" — the platform shows which attack steps went undetected. Any event with no corresponding alert record is a detection gap.

### Alert model fields

`alert_id`, `simulation_id`, `event_id` (triggering event FK), `rule_id`, `severity`, `type`, `title`, `description`, `affected_node_id`, `created_at`, `acknowledged`

## 11. Realtime Communication Architecture

### The problem

HTTP is request/response: the browser asks, the server answers. For real-time attack events, the server needs to push data to the browser without the browser asking. WebSockets solve this by keeping a persistent bidirectional connection open.

### The solution

The **WebSocket Gateway** holds persistent connections from browser clients. It subscribes to Redis channels and routes messages from Redis to the appropriate browser connections. The API Service never talks to the browser over WebSocket — that is the Gateway's exclusive job.

### Room model

Each simulation has a "room" identified by `simulation_id`. A browser connects to `ws://{host}/ws/{simulation_id}?token={jwt}`. The Gateway tracks which connections belong to which room and only forwards events to the correct room.

---

## 12. WebSocket System Overview

### Connection lifecycle

1. Browser opens `ws://.../ws/{simulation_id}?token={jwt}`
2. Gateway validates the JWT
3. Gateway adds the connection to the room for `simulation_id`
4. Gateway sends `STATE_SYNC` with current simulation state
5. Gateway subscribes to `simulation:{sim_id}:events` and `alerts:{sim_id}` Redis channels
6. Events from Redis are forwarded to all connections in the room
7. On disconnect: connection removed from the room

### Message protocol — Server → Client

| Message type | When sent | Key payload fields |
|---|---|---|
| `ATTACK_EVENT` | Every simulation step | `event_id`, `type`, `source_node`, `target_node`, `ttp_id`, `severity`, `timestamp` |
| `NODE_STATE_CHANGE` | When a node's health changes | `node_id`, `old_state`, `new_state`, `timestamp` |
| `ALERT_FIRED` | When a detection rule triggers | `alert_id`, `title`, `severity`, `affected_node_id`, `timestamp` |
| `SIMULATION_STATUS` | On start / pause / complete | `simulation_id`, `status`, `timestamp` |
| `STATE_SYNC` | On connect / reconnect / seek | Full topology JSON + node state map |

### Message protocol — Client → Server

| Message type | Effect |
|---|---|
| `PAUSE` | Published as command to Redis → Simulation Engine pauses |
| `RESUME` | Published as command → engine resumes |
| `STOP` | Published as command → engine stops |
| `SEEK {timestamp}` | Sent to Replay Engine → seek playback to timestamp |
| `HEARTBEAT` | Acknowledged; keeps connection alive |

### Auto-reconnect

The browser WebSocket client retries on disconnect. The Gateway sends `STATE_SYNC` on reconnect so the client catches up without missing events.

## 13. Telemetry & Metrics Architecture

### What we measure

- Events generated per second (simulation throughput)
- Active WebSocket connections per simulation
- Alert rule evaluation latency
- API endpoint response times (P50, P95, P99)
- Database query duration
- Redis Pub/Sub lag (time from publish to consumer receipt)
- Celery task queue depth

### How we measure it

**Prometheus** — A metrics collection system. Each service exposes a `/metrics` endpoint that Prometheus scrapes on a fixed interval. FastAPI services use `prometheus-fastapi-instrumentator` for automatic HTTP metrics. Custom metrics use the `prometheus_client` Python library.

**Grafana** — Reads from Prometheus and renders dashboards. Key dashboards: simulation throughput, WebSocket health, alert pipeline, database performance.

### In MVP

Prometheus and Grafana run in Docker Compose. Dashboards are minimal (HTTP response times + Celery queue depth). Full dashboards are Phase 5.

## 14. Database Architecture

### PostgreSQL as the system of record

PostgreSQL is the durable, permanent store. Every event, alert, simulation, replay, and user lives here. Redis is ephemeral — Pub/Sub messages disappear after delivery. PostgreSQL is permanent.

### Redis as the fast layer

Redis serves two roles:
1. **Event bus** — Pub/Sub channels carry events between services in real time
2. **Task broker + cache** — Celery uses Redis as its task queue; also stores JWT blocklists and simulation state snapshots

### SQLAlchemy 2.x async ORM

All DB access uses SQLAlchemy's async API (`AsyncSession`, `AsyncEngine`, `asyncpg` driver). This keeps FastAPI's async event loop from blocking on database queries.

## 15. Core Database Tables

### `scenarios`
`id` (UUID PK), `name`, `description`, `kill_chain_phases` (JSON array), `steps` (JSON array of step definitions), `created_at`

Seeded from YAML files at startup. Not created by users in MVP.

### `simulations`
`id` (UUID PK), `user_id` (FK → users), `scenario_id` (FK → scenarios), `status` (enum: INITIALIZING / RUNNING / PAUSED / COMPLETED / STOPPED), `topology` (JSONB — node list + edges), `attack_speed` (float multiplier), `started_at`, `completed_at`

### `events`
`id` (UUID PK), `simulation_id` (FK → simulations), `sequence_number` (int — ordering within sim), `type` (RECON / LATERAL_MOVEMENT / EXFILTRATION / etc.), `severity` (LOW / MEDIUM / HIGH / CRITICAL), `source_node_id` (string), `target_node_id` (string), `ttp_id` (string, e.g. T1078), `raw_data` (JSONB — extra metadata), `occurred_at` (timestamp with timezone)

**Critical indexes:**
- `(simulation_id, sequence_number)` — ordered replay queries
- `(simulation_id, type)` — filter by event type
- `(simulation_id, target_node_id)` — filter by node

### `alerts`
`id` (UUID PK), `simulation_id` (FK), `event_id` (FK → events, the trigger), `rule_id` (FK → detection_rules), `severity`, `title`, `description`, `affected_node_id`, `created_at`, `acknowledged` (bool, default false)

### `detection_rules`
`id` (UUID PK), `name`, `description`, `event_type_filter` (string or JSON array), `severity_min` (enum), `alert_title`, `alert_severity`, `enabled` (bool)

### `replays`
`id` (UUID PK), `simulation_id` (FK, unique), `title`, `event_count` (int), `duration_ms` (int), `created_at`

## 18. API Layer Responsibilities

The API Service is the only service the browser talks to over HTTP.

- **Authentication** — login, register, JWT issuance, token refresh, JWT validation dependency
- **Simulation management** — create, list, get, start, pause, stop simulations
- **Scenario management** — list pre-built scenarios, get scenario detail
- **Replay management** — list saved replays, get replay metadata, trigger playback
- **Alert querying** — get alerts for a simulation (paginated)
- **Event querying** — get the event log for a simulation (paginated, filterable)
- **Input validation** — all request bodies go through Pydantic schemas before touching the DB
- **Authorization** — every protected endpoint checks the JWT before processing

The API Service does **not** run simulations directly. It publishes a `START_SIMULATION` Celery task and returns immediately. The Simulation Engine does the actual work asynchronously.

---

## 19. Simulation Engine Responsibilities

- Receive `run_simulation(simulation_id)` tasks from the Celery queue
- Build the virtual topology from the scenario config
- Run the attack state machine step by step
- Generate Event objects from scenario step definitions
- Write each Event to PostgreSQL immediately
- Publish each Event to Redis immediately
- Update in-memory node health states
- Publish `NODE_STATE_CHANGE` events when states change
- Listen on the commands channel for PAUSE / RESUME / STOP
- On completion: update `Simulation.status = COMPLETED`, create Replay record, publish `SIMULATION_STATUS(COMPLETED)`

---

## 20. Event Engine Responsibilities

The event engine is the part of the Simulation Engine that constructs valid Event objects from abstract scenario step definitions.

- Map step definitions to concrete Event objects
- Assign monotonically increasing sequence numbers within a simulation
- Resolve source and target nodes from the current topology state
- Set `occurred_at` to the wall clock time at generation
- Attach MITRE ATT&CK TTP IDs from the scenario step
- Determine severity
- Write to PostgreSQL
- Serialize to JSON for Redis publication

---

## 21. Replay Engine Responsibilities

- Expose REST endpoints: play, pause, seek, set speed
- Read the ordered event log from PostgreSQL (`ORDER BY sequence_number`)
- Re-publish events to Redis at controlled intervals respecting the speed multiplier
- On seek: compute node state at the target timestamp, publish `STATE_SYNC`, resume forward
- Track replay cursor position (current sequence number) in Redis
- Support multiple concurrent replay sessions (different users, different simulations)

## 22. Data Flow Between Systems

### Live simulation

```
Browser POST /api/simulations/{id}/start
  → API: validates JWT, sets Simulation.status = RUNNING
  → API: dispatches run_simulation task to Celery via Redis

Celery picks up task → Simulation Engine starts
  → Engine: generates topology, publishes SIMULATION_STATUS(RUNNING)
  → WS Gateway receives → sends SIMULATION_STATUS to browser

Engine: step loop begins
  → builds Event → writes to PostgreSQL → publishes to Redis
  → WS Gateway: forwards ATTACK_EVENT to browser
  → Alert Service: evaluates rules → maybe fires ALERT_FIRED → browser
  → Engine: updates node state → publishes NODE_STATE_CHANGE
  → WS Gateway: forwards NODE_STATE_CHANGE to browser

Engine: all steps done
  → sets Simulation.status = COMPLETED
  → creates Replay record
  → publishes SIMULATION_STATUS(COMPLETED) → browser
```

### Replay

```
Browser opens Replay Viewer → connects to WS /ws/replay/{replay_id}
Browser POST /api/replays/{id}/play

Replay Engine: reads events from PostgreSQL (ORDER BY sequence_number)
  → publishes event to Redis
  → WS Gateway: forwards ATTACK_EVENT to browser
  → waits (delay_ms / speed_multiplier)
  → publishes next event ... (loop until end)

Browser scrubs timeline → POST /api/replays/{id}/seek?ts=1234567
  → Replay Engine: stops playback
  → queries NODE_STATE_CHANGE events up to ts → reconstructs state
  → publishes STATE_SYNC → browser re-renders topology
  → resumes playback from seek point
```

## 24. Full Attack Flow Lifecycle

```
Phase: INITIALIZING
  User selects "Lateral Movement" scenario, sets attack speed 1x, hits Launch
  API: creates Simulation record (status=INITIALIZING)
  Celery: dispatches run_simulation task
  Engine: builds topology — 8 nodes (attacker, 2 workstations, 2 servers, 1 DB, 1 router, 1 IAM)
  Engine: saves topology JSON to Simulation record
  Engine: publishes STATE_SYNC → browser renders empty topology
  Engine: transitions to RUNNING

Phase: RUNNING

  Step 1 — RECON (severity: LOW)
    Source: Attacker  Target: all nodes (network scan)
    Event written to DB, published to Redis
    Browser: attacker node animates, no node state changes
    Alert: no rule matches RECON + LOW → detection gap

  Step 2 — INITIAL_ACCESS (severity: HIGH)
    Source: Attacker  Target: Workstation-1 (phishing)
    Workstation-1 → COMPROMISED
    Alert: "Initial Access Detected" → browser alert feed

  Step 3 — EXECUTION (severity: HIGH)
    Source: Workstation-1 (malicious script)
    No new node compromise, same node
    Alert: "Code Execution on Workstation-1"

  Step 4 — LATERAL_MOVEMENT (severity: CRITICAL)
    Source: Workstation-1  Target: Server-1
    Server-1 → SUSPICIOUS
    Alert: "Lateral Movement: Workstation-1 → Server-1"

  Step 5 — PRIVILEGE_ESCALATION (severity: CRITICAL)
    Source: Server-1 (root escalation)
    Server-1 → COMPROMISED
    Alert: "Privilege Escalation on Server-1"

  Step 6 — LATERAL_MOVEMENT (severity: CRITICAL)
    Source: Server-1  Target: Database-1
    Database-1 → COMPROMISED
    Alert: "Lateral Movement to Database"

  Step 7 — COLLECTION (severity: HIGH)
    Source: Database-1 (data staged)
    Alert: "Data Collection on Database-1"

  Step 8 — EXFILTRATION (severity: CRITICAL)
    Source: Database-1  Target: Attacker (external)
    Alert: "Data Exfiltration Detected"

Phase: COMPLETED
  Engine: sets Simulation.status = COMPLETED
  Engine: creates Replay record (event_count=8, duration_ms=~12000)
  Engine: publishes SIMULATION_STATUS(COMPLETED)
  Browser: shows completion overlay, prompts user to open replay
```

## 25. Replay Flow Lifecycle

```
1. User opens Replay Library → GET /api/replays → card grid of saved simulations
2. User selects "Lateral Movement — 2026-05-14"
3. Browser renders empty topology (same layout as original sim, from Simulation.topology)
4. User presses Play → POST /api/replays/{id}/play
5. Replay Engine:
     reads ALL events for simulation_id ORDER BY sequence_number
     starts cursor at sequence 0
     loop:
       publishes event to Redis → WS Gateway → browser
       waits event.delay_ms / speed_multiplier
6. Browser: ATTACK_EVENT, NODE_STATE_CHANGE, ALERT_FIRED arrive identically to live sim
7. User drags scrubber to 60% through timeline
     POST /api/replays/{id}/seek?position=0.6
     Engine: computes target sequence_number (0.6 × event_count)
     Engine: loads all NODE_STATE_CHANGE events up to that sequence
     Engine: reconstructs {node_id → state} map
     Engine: publishes STATE_SYNC → browser re-renders topology at that point
     Engine: resumes forward from target sequence
8. User sets speed to 4x → POST /api/replays/{id}/speed?multiplier=4
     All subsequent sleep intervals divided by 4
9. Replay reaches last event → publishes SIMULATION_STATUS(COMPLETED)
```

## 26. PostgreSQL Usage Strategy

### Connection pooling

SQLAlchemy maintains a connection pool (default 5–10 connections). Each async request borrows a connection, runs its query, and returns it. No new TCP connection is opened per request.

### Write strategy

Events are written immediately — no batching in MVP. Each simulation step writes one Event row. This is fine because simulations run at human-perceivable speed (50–500ms between steps), which is far slower than PostgreSQL's write throughput.

Future optimization for high-throughput: batch writes in a buffer and flush every 100ms.

### Read strategy

- **Replay**: keyset pagination cursor (`WHERE sequence_number > {cursor} ORDER BY sequence_number LIMIT 100`) — never use OFFSET on large tables
- **Event timeline UI**: `LIMIT 50` with standard pagination, filterable by type/severity/node
- **State reconstruction**: `SELECT * FROM events WHERE simulation_id = ? AND sequence_number <= ? AND type = 'NODE_STATE_CHANGE'`

### Migrations

Foundation uses `Base.metadata.create_all()` for table creation. Once real models exist, **Alembic** will be added for tracked, versioned, reversible schema migrations. That switch happens before adding the first real feature module.

## 27. Event Storage Strategy

### Why every event is stored

Replay requires the complete event log. There is no summarized version — the raw, ordered, complete event log is the asset.

### The events table as an append-only log

Events are never updated or deleted. Written once, read many times. This is the **append-only event log** pattern — a well-established approach in event-driven systems.

### Indexing

| Index | Covers |
|---|---|
| `(simulation_id, sequence_number)` | All replay queries |
| `(simulation_id, type)` | Filter by event type in UI |
| `(simulation_id, target_node_id)` | "Show events for this node" |

### JSONB for raw_data

The `raw_data` column is JSONB. Stores any extra event metadata (tool used, payload hash, scan results) without requiring a schema change for every new event type.

## 28. Infrastructure Node Management

### Node schema (JSON)

```json
{
  "id": "node-uuid",
  "type": "SERVER | DATABASE | ROUTER | IAM | WORKSTATION | ATTACKER",
  "label": "Web Server 1",
```

### Where nodes live

- **During simulation**: in-memory dictionary in the Celery worker (`{node_id: NodeState}`)
- **Persisted**: full topology JSON in `simulations.topology`, plus all state transitions in the event log
- **For replay**: reconstructed from `NODE_STATE_CHANGE` events in PostgreSQL

### Node types and attack roles

| Type | Role |
|---|---|
| ATTACKER | Origin of all attacks; never becomes compromised |
| WORKSTATION | Common initial access target |
| SERVER | Lateral movement destination |
| DATABASE | Data collection / exfiltration target |
| ROUTER | Network traversal pivot |
| IAM | Privilege escalation target |

## 29. Attack Propagation Logic

### How the attack moves

The engine selects source and target nodes based on the scenario step's `source_node_type` and `target_node_type` and the current live node states:

- `source_node_type: ATTACKER` → always the attacker node
- `source_node_type: COMPROMISED` → pick any currently COMPROMISED non-attacker node (the foothold)
- `target_node_type: DATABASE` → pick a HEALTHY or SUSPICIOUS database node (prefers HEALTHY)

This makes propagation realistic: the attacker uses each compromised foothold to reach deeper nodes.

### Probability

Steps with `probability < 1.0` may be skipped. `probability: 0.8` means a 20% chance the step is omitted. Two runs of the same scenario produce slightly different event logs, adding educational variety.

### Attack speed multiplier

Set by the user at launch (0.5x to 4x in MVP). All `delay_ms` values are divided by this multiplier. The engine never modifies the scenario definition — it just adjusts sleep duration at runtime.

## 30. Severity & Alert Logic

### Severity levels

| Level | Meaning |
|---|---|
| LOW | Reconnaissance, scanning — looking, not acting |
| MEDIUM | Suspicious activity — could be malicious or noise |
| HIGH | Likely malicious — credential theft, execution, lateral movement |
| CRITICAL | Confirmed breach — data exfiltration, full node compromise |

### Node state transition thresholds

- LOW / MEDIUM event targeting a HEALTHY node → node becomes **SUSPICIOUS**
- HIGH / CRITICAL event → node becomes **COMPROMISED** (skips SUSPICIOUS if HEALTHY)
- Subsequent HIGH / CRITICAL on already SUSPICIOUS node → **COMPROMISED**

### Detection gap view

Any event with no corresponding Alert record is a detection gap. The Replay UI can show a breakdown of all events colored by whether they triggered an alert or not.

## 31. Future Scalability Considerations

### Current MVP design

- Single Celery worker: 5–10 concurrent simulations
- Single Redis: all Pub/Sub
- Single PostgreSQL: all writes
- Single WebSocket Gateway: hundreds of concurrent connections (asyncio handles this well)

### Scaling paths

| Bottleneck | Solution |
|---|---|
| More concurrent simulations | Add Celery workers — Redis broker distributes tasks automatically |
| More WS connections | Run multiple Gateway instances behind a load balancer — all subscribe to same Redis channels |
| Large event volumes | Partition `events` table by `simulation_id`; or move to TimescaleDB |
| Event bus at scale | Replace Redis Pub/Sub with Kafka — ordered, durable, replayable streams |
| Read-heavy load | Add PostgreSQL read replicas; route SELECTs to replicas |

## 37. Final Backend System Summary

Traceveil's backend is an **event-driven, multi-service Python system** built around one principle: events are the universal currency.

**What the backend is:**
- A **REST API** (FastAPI) — the public HTTP interface. Receives commands, validates them, persists state, delegates simulation work to background workers.
- A **Simulation Engine** (Celery worker) — runs attack state machines, generates events from scenario scripts, writes them to PostgreSQL, broadcasts them through Redis.
- A **WebSocket Gateway** (FastAPI) — bridges Redis and browser clients. Holds open persistent connections. Forwards events in real time.
- An **Alert Service** — evaluates detection rules against the live event stream. Fires alerts back through the same pipeline.
- A **Replay Engine** — re-publishes stored events from PostgreSQL at controlled speed. Supports seek and speed control.

**What the data stores do:**
- **PostgreSQL** — durable record of everything: every event, simulation, user, alert, and replay.
- **Redis** — fast, ephemeral backbone: task broker for Celery, Pub/Sub bus between services, cache for session state.

**Why this design works:**

Whether a simulation is live or being replayed, the browser receives the same event shapes through the same WebSocket protocol. The replay system is not a special mode — it is just the same event pipeline driven by stored data instead of a live engine. This keeps the frontend simple and the entire system testable end-to-end with a single event schema.

The modular service boundaries mean each piece can be developed, tested, scaled, and debugged independently. The event-driven communication means no service is coupled to the internal implementation of any other.

This is the architecture that the implementation will be built on.
